## Codebase Patterns
- Build gates: `npm run build` (tsc + vite) at repo root, `cargo check` inside src-tauri/.
- NEVER remove src-tauri/.cargo/config.toml, lib-patch/, or sdk-patch/ - they patch a damaged
  VS/Windows SDK install (AV-quarantined files). Full `npm run tauri build` only in the final story.
- Overlay state flows Rust -> webview via overlay.eval in recorder.rs update_overlay; the webview
  is a pure renderer keyed off data-state. Animations: transform/opacity only. No polling loops.
- The spec for all UX stories is docs/RESEARCH-wispr-superwhisper.md (section numbers referenced
  from prd.json).
- whisper-server sidecar needs the ggml/whisper DLLs beside the exe; they are bundle resources in
  tauri.conf.json and already copied into target/release for dev runs.
- Overlay state names (Rust RecordingState -> data-state): Ready->idle, Recording->listening,
  Transcribing->processing; 'done' pre-mounted for US-008. New pill states = add a .layer div in
  overlay.html + a #mic[data-state=X] .state-X CSS rule; layers crossfade automatically.
- data-tauri-drag-region only works if the element with the attribute is the mousedown target:
  keep `pointer-events: none` on ALL layer children, and only the active layer has
  pointer-events: auto.
- Settings fields owned by the RUST side (currently overlayX/overlayY) must be re-asserted in
  save_settings: main.ts caches the whole Settings object at page load and sends that stale
  snapshot on every save, which would silently revert Rust-side changes. Frontend-owned fields
  round-trip fine (the JS object keeps unknown fields).
- Win32 interop: add `windows = "0.61"` (same version tao/wry already pull; features
  Win32_Foundation + Win32_UI_WindowsAndMessaging are already enabled by tao, so cargo check
  stays fast). Bin-only modules (needing AppState) are declared with `mod x;` in main.rs, NOT
  in lib.rs.
- Overlay interactivity: window is click-through by default; pill_hittest.rs (WH_MOUSE_LL) flips
  it over the pill rect. If you change #mic geometry in overlay.html, update the PILL_* consts
  in pill_hittest.rs.
- Tauri v2 event targeting (verified in tauri-2.10.3 source, manager/mod.rs emit_to filter):
  emit_to("overlay", ...) is ONLY delivered to listeners scoped to that label
  (getCurrentWebviewWindow().listen or listen(..., { target: 'overlay' })). A plain
  __TAURI__.event.listen registers target Any and silently receives NOTHING from emit_to.
  Conversely app.emit broadcasts to every webview. Match the pair or events vanish.
- overlay.html JS lives in a plain inline <script> (no type=module, no imports, uses the
  window.__TAURI__ global from withGlobalTauri) - vite passes it through untouched in build.
- OVERLAY WEBVIEW CONTRACT (pre-mounted 2026-07-20, Rust side still TODO): status dot is driven
  by emit_to("overlay", "status-dot", payload) with payload 'starting'|'processing'|'done'|'off'
  (listener is overlay-scoped, sets #mic dataset.dot). confirm-discard and paste-fallback state
  layers exist in overlay.html (data-state values 'confirm-discard' / 'paste-fallback'). Quick
  menu opens on left-click of the pill, sets data-menu="open" on #mic while open (pill_hittest
  should widen the hit rect to host bounds while that attribute is set), and invokes these EXACT
  Rust command names: menu_hide_hour, menu_paste_last, menu_open_settings, menu_quit.
- Hotkey Pressed handler pattern (US-004): compute will_start + read settings ONCE in a single
  lock scope, set overlay state + play the start ping SYNCHRONOUSLY in the closure, and only
  then spawn the async task that touches audio/model I/O. US-005/US-006 timer/cancel logic
  belongs in that synchronous prefix, not inside the spawned async block. Note: main.rs
  duplicates the overlay-state eval string from recorder.rs's private helper - keep in sync.
- Settings wire format is camelCase via explicit #[serde(rename)] per field (interactionSounds,
  overlayVisible, whisperModel...); Rust field names stay snake_case. Follow that convention for
  any new field, and add a compat test (old config without the field must still deserialize).
- Interaction sounds: src-tauri/src/sounds.rs embeds start.wav/stop.wav ('static via
  include_bytes!) and plays through winmm PlaySoundW SND_ASYNC|SND_MEMORY|SND_NODEFAULT -
  non-blocking, no audio crate. Call sounds::play_start(enabled)/play_stop(enabled).
- recording_mode gesture state (US-005): AppState carries ONE hotkey_gesture: Mutex<enum
  {Idle, Pressed(Instant), HandsFree}> for the "auto" tap/hold discrimination - NOT two
  independently-locked fields (a Mutex<Option<Instant>> + a separate AtomicBool). Code
  review caught that two separate locks let a fast Pressed/Released pair observe an
  in-between combination that could never occur in true wall-clock order (TOCTOU between
  the two locks). One enum behind one lock makes the whole read-decide-mutate step atomic.
  Tap-vs-hold needs NO timer/sleep - it's decided by comparing Instant::now() at the Pressed
  and Released event boundaries the OS already delivers, so it stays fully event-driven.
  "auto" is additive: the existing "toggle" and "push-to-talk" branches are untouched, so
  legacy explicit settings behave exactly as before.
- Pattern: whenever a gesture/state machine needs 2+ pieces of correlated mutable state
  read together to make one decision (e.g. "is this a second tap"), put them in ONE enum
  behind ONE lock, not N independently-synchronized fields - even if each field's own
  updates look atomic in isolation, the multi-field READ can still observe a torn
  combination. Use code-reviewer proactively on new concurrent/event-driven state machines
  before committing; it caught this one.
- cargo test --lib only exercises typr_lib (settings.rs, recorder.rs, etc.) - main.rs is the
  bin crate and has no unit tests; `cargo check` (checks all targets incl. the bin) is the
  gate that actually compiles the hotkey closure in main.rs.
- CRITICAL Win32 global-shortcut gotcha (US-006): tauri-plugin-global-shortcut's
  GlobalHotKeyEvent dispatch (verified in the 2.3.1 + global-hotkey 0.7.0 source in the local
  cargo registry cache) holds a lock on its OWN internal shortcuts-map Mutex for the entire
  duration of a shortcut's handler closure, and on Windows that closure runs synchronously on
  the main thread's WndProc (WM_HOTKEY). Calling app.global_shortcut().register/unregister/
  on_shortcut SYNCHRONOUSLY from inside a shortcut's own handler closure re-locks that same
  non-reentrant Mutex on the same thread -> self-deadlock, freezing the whole app (not just the
  feature). Any register/unregister triggered in response to a shortcut event MUST be deferred
  via tauri::async_runtime::spawn so it runs after the closure returns and releases the lock.
  This applies to ANY future story that registers per-state global shortcuts (the confirm-
  discard/second-Esc path and the main hotkey already follow this rule).
- Ordering gotcha for any "cancel/discard while state X, gated re-entry on state Y" flow (found
  by code-reviewer on US-006's cancel_recording, real HIGH-severity race): if state must not
  flip to the gate value (e.g. Ready) until some cleanup step (e.g. unregistering a shortcut)
  finishes, do the cleanup BEFORE flipping state, not after - otherwise a fast re-entry (new
  recording starting) can race the stale cleanup and end up in a corrupted config (e.g. its
  fresh registration clobbered by the old unregister, or vice versa). Symmetric to the US-005
  "one enum behind one lock" lesson but about *ordering within one path*, not lock granularity.

## 2026-07-19 - US-002

  set_ignore_cursor_events(true) right after the overlay is created, and installs a WH_MOUSE_LL
  low-level mouse hook (windows crate 0.61, main thread, installed once in setup, uninstalled in
  RunEvent::Exit). The hook reads a cached pill screen rect (4 AtomicI32s, physical px) on every
  WM_MOUSEMOVE and flips ignore_cursor_events only when the inside/outside answer changes,
  dispatched via run_on_main_thread. The rect cache is refreshed ONLY from window
  Moved/ScaleFactorChanged events - no timers, no polling, no JS involvement.
- Hit rect is 200x48 logical px centered on the pill (pill center = 36px above host bottom,
  widest state 180px + grab margin), converted to physical using the overlay's scale factor.
- Dragging: WM_LBUTTONDOWN inside the rect sets a DRAGGING flag (hook never flips to
  click-through mid-drag - the window chases the cursor and the rect cache lags); WM_LBUTTONUP
  ends the drag -> clamp_and_persist() clamps the window into Monitor::work_area() (tauri 2.10
  has work_area + monitor_from_point, no extra Win32 needed) and persists overlayX/overlayY
  (physical px, Option<i32>) into config.json off the main thread. Plain clicks take the same
  path but skip both set_position and the disk write (no change detected).
- Startup: pill_hittest::restore_position() reapplies the saved position clamped into the work
  area of the monitor that now contains the point (monitor_from_point); if that monitor is gone,
  the default bottom-center placement stands. save_settings() re-asserts the live overlay_x/y
  over the incoming frontend settings (main.ts sends a stale page-load snapshot on every save).
- Files changed: src-tauri/src/pill_hittest.rs (new, bin-crate module), src-tauri/src/main.rs,

## 2026-07-20 - US-006 (Esc cancel with 30-second discard guard)
- recorder.rs: Recorder gained recording_started_at (Arc<Mutex<Option<Instant>>>, tracked in
  Recorder per the US-005 learning above, NOT sharing main.rs's hotkey_gesture) and a
  cancel_guard: Arc<Mutex<CancelGuard>> (None / ConfirmDiscard(Instant)). start_recording now
  stamps recording_started_at and registers the "Escape" global shortcut (arm_cancel_shortcut);
  both cancel_recording and the top of stop_and_transcribe unregister it - Escape is never
  globally registered while idle. Esc under 30s elapsed -> instant cancel (new
  AudioRecorder::cancel() in audio.rs drops the cpal stream and clears samples without writing
  a WAV, mirroring stop_and_save's teardown). Esc past 30s: first press sets overlay
  data-state=confirm-discard (already pre-mounted in overlay.html) and arms a 3s
  tokio::time::sleep auto-revert-to-listening timer, debounced against a fresher arm/clear via
  an armed_at Instant token; a second Esc while armed discards immediately. Pulled
  update_overlay's eval string into a small set_overlay_state(app, name) helper so the
  confirm-discard/listening evals reuse it instead of duplicating the JS format string.
- Files changed: src-tauri/src/recorder.rs, src-tauri/src/audio.rs, prd.json, progress.txt.
- Checks: cargo check clean; cargo test --lib 24/24 pass; npm run build exit 0.
- Code-reviewed (concurrency-focused pass, since this story registers/unregisters a global
  shortcut from application code for the first time): confirmed correct that
  tauri-plugin-global-shortcut's event dispatch holds its own internal shortcuts-map lock for
  the whole duration of a shortcut handler closure (main-thread WndProc on Windows), so
  register/unregister must never be called synchronously from inside that closure - see the
  new Codebase Patterns entry above. The review also caught a real HIGH-severity ordering race
  in the first draft of cancel_recording (state flipped to Ready, unblocking a fresh
  start_recording/re-registration, BEFORE the old Escape registration had finished being torn
  down) - fixed by unregistering before flipping state to Ready. Also tightened the 3s
  auto-revert timer to double-check state==Recording (not just the CancelGuard token) before
  reverting the overlay, closing a narrower cosmetic race against a concurrent second-Esc
  discard. NOT verified at runtime (no browser/UI tools this iteration): actual Esc-under-30s,
  first-Esc-past-30s-then-timeout, first-Esc-past-30s-then-second-Esc, and rapid
  cancel-then-restart all need a manual dev run; US-011 covers the end-to-end launch check.
- **Learnings for future iterations:**
  - Any future story that registers a global shortcut dynamically (not just once at startup)
    must follow the defer-via-async_runtime::spawn rule above - it is easy to get right at
    compile time (cargo check/test can't catch the self-deadlock) and easy to get wrong at
    runtime, so treat any new on_shortcut/register/unregister call site as needing a
    code-reviewer pass before commit, the same way US-005's lock consolidation did.
  - "Discard now" is idempotent by construction in cancel_recording (cancelling an
    already-stopped stream, clearing an already-None Option, unregistering an
    already-unregistered shortcut are all safe no-ops) - this is what makes it safe for two
    near-simultaneous Esc presses to both spawn a cancel task without extra de-duplication.
    Keep new cancel/teardown paths idempotent for the same reason rather than adding explicit
    de-dup locking.
