## Codebase Patterns
- Build gates: `npm run build` (tsc + vite) at repo root, `cargo check` inside src-tauri/.
- NEVER remove src-tauri/.cargo/config.toml, lib-patch/, or sdk-patch/ - they patch a damaged
  VS/Windows SDK install (AV-quarantined files). Full `npm run tauri build` only in the final story.
- Overlay state flows Rust -> webview via overlay.eval in recorder.rs update_overlay; the webview
  is a pure renderer keyed off data-state. Animations: transform/opacity only. No polling loops.
- The spec for all UX stories is docs/RESEARCH-wispr-superwhisper.md (section numbers referenced
  from prd.json).
- whisper-server sidecar needs the ggml/whisper DLLs beside the exe; they are bundle resources in
  tauri.conf.json and already copied into target/release for dev runs.
- Overlay state names (Rust RecordingState -> data-state): Ready->idle, Recording->listening,
  Transcribing->processing; 'done' pre-mounted for US-008. New pill states = add a .layer div in
  overlay.html + a #mic[data-state=X] .state-X CSS rule; layers crossfade automatically.
- data-tauri-drag-region only works if the element with the attribute is the mousedown target:
  keep `pointer-events: none` on ALL layer children, and only the active layer has
  pointer-events: auto.
- Settings fields owned by the RUST side (currently overlayX/overlayY) must be re-asserted in
  save_settings: main.ts caches the whole Settings object at page load and sends that stale
  snapshot on every save, which would silently revert Rust-side changes. Frontend-owned fields
  round-trip fine (the JS object keeps unknown fields).
- Win32 interop: add `windows = "0.61"` (same version tao/wry already pull; features
  Win32_Foundation + Win32_UI_WindowsAndMessaging are already enabled by tao, so cargo check
  stays fast). Bin-only modules (needing AppState) are declared with `mod x;` in main.rs, NOT
  in lib.rs.
- Overlay interactivity: window is click-through by default; pill_hittest.rs (WH_MOUSE_LL) flips
  it over the pill rect. If you change #mic geometry in overlay.html, update the PILL_* consts
  in pill_hittest.rs.
- Tauri v2 event targeting (verified in tauri-2.10.3 source, manager/mod.rs emit_to filter):
  emit_to("overlay", ...) is ONLY delivered to listeners scoped to that label
  (getCurrentWebviewWindow().listen or listen(..., { target: 'overlay' })). A plain
  __TAURI__.event.listen registers target Any and silently receives NOTHING from emit_to.
  Conversely app.emit broadcasts to every webview. Match the pair or events vanish.
- overlay.html JS lives in a plain inline <script> (no type=module, no imports, uses the
  window.__TAURI__ global from withGlobalTauri) - vite passes it through untouched in build.
- OVERLAY WEBVIEW CONTRACT (pre-mounted 2026-07-20, Rust side still TODO): status dot is driven
  by emit_to("overlay", "status-dot", payload) with payload 'starting'|'processing'|'done'|'off'
  (listener is overlay-scoped, sets #mic dataset.dot). confirm-discard and paste-fallback state
  layers exist in overlay.html (data-state values 'confirm-discard' / 'paste-fallback'). Quick
  menu opens on left-click of the pill, sets data-menu="open" on #mic while open (pill_hittest
  should widen the hit rect to host bounds while that attribute is set), and invokes these EXACT
  Rust command names: menu_hide_hour, menu_paste_last, menu_open_settings, menu_quit.
- Hotkey Pressed handler pattern (US-004): compute will_start + read settings ONCE in a single
  lock scope, set overlay state + play the start ping SYNCHRONOUSLY in the closure, and only
  then spawn the async task that touches audio/model I/O. US-005/US-006 timer/cancel logic
  belongs in that synchronous prefix, not inside the spawned async block. Note: main.rs
  duplicates the overlay-state eval string from recorder.rs's private helper - keep in sync.
- Settings wire format is camelCase via explicit #[serde(rename)] per field (interactionSounds,
  overlayVisible, whisperModel...); Rust field names stay snake_case. Follow that convention for
  any new field, and add a compat test (old config without the field must still deserialize).
- Interaction sounds: src-tauri/src/sounds.rs embeds start.wav/stop.wav ('static via
  include_bytes!) and plays through winmm PlaySoundW SND_ASYNC|SND_MEMORY|SND_NODEFAULT -
  non-blocking, no audio crate. Call sounds::play_start(enabled)/play_stop(enabled).

## 2026-07-19 - US-002
- Overlay is now click-through by default: pill_hittest::install() calls
  set_ignore_cursor_events(true) right after the overlay is created, and installs a WH_MOUSE_LL
  low-level mouse hook (windows crate 0.61, main thread, installed once in setup, uninstalled in
  RunEvent::Exit). The hook reads a cached pill screen rect (4 AtomicI32s, physical px) on every
  WM_MOUSEMOVE and flips ignore_cursor_events only when the inside/outside answer changes,
  dispatched via run_on_main_thread. The rect cache is refreshed ONLY from window
  Moved/ScaleFactorChanged events - no timers, no polling, no JS involvement.
- Hit rect is 200x48 logical px centered on the pill (pill center = 36px above host bottom,
  widest state 180px + grab margin), converted to physical using the overlay's scale factor.
- Dragging: WM_LBUTTONDOWN inside the rect sets a DRAGGING flag (hook never flips to
  click-through mid-drag - the window chases the cursor and the rect cache lags); WM_LBUTTONUP
  ends the drag -> clamp_and_persist() clamps the window into Monitor::work_area() (tauri 2.10
  has work_area + monitor_from_point, no extra Win32 needed) and persists overlayX/overlayY
  (physical px, Option<i32>) into config.json off the main thread. Plain clicks take the same
  path but skip both set_position and the disk write (no change detected).
- Startup: pill_hittest::restore_position() reapplies the saved position clamped into the work
  area of the monitor that now contains the point (monitor_from_point); if that monitor is gone,
  the default bottom-center placement stands. save_settings() re-asserts the live overlay_x/y
  over the incoming frontend settings (main.ts sends a stale page-load snapshot on every save).
- Files changed: src-tauri/src/pill_hittest.rs (new, bin-crate module), src-tauri/src/main.rs,
  src-tauri/src/settings.rs (+2 fields, +2 tests), src-tauri/Cargo.toml (windows dep),
  src/overlay.html (geometry-sync comment only), prd.json, progress.txt.
- Checks: npm run build exit 0; cargo check clean (1.7s - tao already enables the windows-crate
  features); cargo test --lib settings: 6/6 pass incl. new pre-US-002-config compat and
  overlay-pos roundtrip tests. NOT verified at runtime (no browser/UI tools this iteration):
  actual hover hit-testing, dragging, and persistence need a manual dev run; US-011 covers the
  end-to-end launch check.
- **Learnings for future iterations:**
  - The US-001 click-swallowing regression is now closed; the overlay never intercepts clicks
    outside the 200x48 pill zone.
  - WH_MOUSE_LL callbacks must stay cheap (slow hooks lag the system cursor): keep the hook side
    to atomic reads and only dispatch on state flips. tauri's run_on_main_thread executes inline
    when already on the main thread - fine here (SetWindowLongPtr-level work).
  - If US-009's right-click menu needs the whole 440x160 host to be interactive while the menu
    is open, add a "menu open" flag the hook respects (widen the hit rect to the host bounds)
    rather than bypassing the hook.
  - Hook install failure leaves the overlay click-through (pill unclickable but dictation
    working) - deliberately NOT falling back to a fully-interactive 440x160 host.
  - windows crate handle types wrap *mut c_void in 0.61 (HHOOK(ptr)); store as isize in an
    AtomicIsize for statics.
